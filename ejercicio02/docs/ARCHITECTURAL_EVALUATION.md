# Evaluación arquitectónica

La arquitectura actual —monolito server-side en Node.js, Express y EJS, con acceso directo a PostgreSQL mediante `pg`— es adecuada para una librería académica de este alcance. La aplicación entrega HTML completo, mantiene autenticación, catálogo y administración dentro de un solo proceso y organiza las rutas por módulos. Esto coincide con la restricción explícita de no exponer REST, GraphQL, SOAP ni formatos de intercambio JSON/XML. Aunque el código no implementa capas MVC formales y separadas en todos los módulos, las vistas EJS, las rutas/controladores y PostgreSQL forman una separación suficiente para un equipo pequeño y un ejercicio centrado en integración y normalización.

Su principal ventaja es la baja complejidad operativa. Se despliega una aplicación Node.js, una base PostgreSQL y un directorio de uploads, opcionalmente detrás de Nginx o Apache. Hay una sola configuración de sesiones, seguridad, errores y acceso a datos. Las transacciones que crean o actualizan libros y sus relaciones se ejecutan contra la misma base sin coordinación distribuida. Diagnosticar una solicitud también es directo: navegador, ruta Express, consulta parametrizada y plantilla EJS pertenecen al mismo repositorio y proceso.

Una solución desacoplada por componentes podría conservar un backend único pero separar una interfaz cliente, por ejemplo una SPA. Eso permitiría evolucionar la presentación de forma más independiente y reutilizar servicios para otros clientes. Sin embargo, introduciría un contrato de API, serialización, CORS, autenticación entre orígenes, compilación del frontend y duplicación de validaciones. Para este proyecto, que exige HTML renderizado en servidor y no necesita clientes móviles ni integraciones públicas, esos costos superan el beneficio. La UI EJS ofrece navegación simple, menor cantidad de JavaScript enviado y una superficie de ataque más acotada.

Los microservicios serían todavía menos convenientes. Separar usuarios, catálogo, imágenes y libros obligaría a definir límites de datos, comunicación entre servicios y consistencia de operaciones que hoy son una sola transacción PostgreSQL. También exigiría observabilidad distribuida, versionado de contratos, gestión de secretos por servicio, redes, reintentos, despliegues coordinados y posiblemente colas. Para un equipo pequeño o individual, esa carga reduciría el tiempo disponible para validar requisitos funcionales. Además, las relaciones normalizadas libro–autor, libro–género y libro–concepto son cohesivas y se consultan juntas; dividirlas aumentaría latencia y complejidad sin una demanda demostrada.

En escalabilidad, el monolito tiene límites, pero no son inmediatos. Puede escalar verticalmente y, si los uploads pasan a almacenamiento compartido y las sesiones ya permanecen en PostgreSQL, también puede replicarse detrás de un balanceador. PostgreSQL ofrece índices y optimización suficiente para el volumen previsible. Sólo una carga muy grande o dominios con ritmos de cambio claramente distintos justificarían extraer componentes. Antes de eso conviene medir consultas, paginar resultados, limitar conexiones y optimizar índices.

El mantenimiento favorece al monolito mientras se preserve la modularidad: cambios de esquema, ruta y vista pueden revisarse en conjunto. El riesgo es que las rutas acumulen validación, SQL y control de flujo; puede mitigarse gradualmente con funciones de servicio o repositorio internas, sin cambiar la arquitectura. En seguridad, una sola frontera simplifica cookies, CSRF, Helmet y autorización, aunque un fallo puede afectar toda la aplicación. La defensa depende de controles consistentes, mínimo privilegio en PostgreSQL, validación server-side, protección de uploads y secretos externos al repositorio.

En conclusión, el monolito server-side es la opción proporcional para los requisitos, el tamaño del equipo y el despliegue esperado. Una solución por componentes sería razonable si aparecieran varios clientes; microservicios, sólo con escala y autonomía organizacional comprobadas. Hoy conviene conservar la arquitectura y fortalecer pruebas, validaciones y operación.
