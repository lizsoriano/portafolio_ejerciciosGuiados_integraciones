ARQUITECTURA CLOUD

+ Prompt Engineering

Diseño de una arquitectura híbrida para una aplicación de banca móvil utilizando Inteligencia Artificial

01

Descripción del problema

Una institución financiera desea desarrollar una aplicación de banca móvil moderna que permita a sus clientes consultar saldos, realizar transferencias, recibir notificaciones y administrar operaciones desde dispositivos móviles.

Debido a que la institución ya cuenta con infraestructura bancaria existente, la solución utilizará una arquitectura de nube híbrida. Algunos sistemas críticos permanecerán dentro de la infraestructura local de la institución, mientras que los componentes que requieren mayor escalabilidad y disponibilidad se ejecutarán en AWS.

La arquitectura debe incluir aplicación móvil, APIs, autenticación, almacenamiento, bases de datos, funciones serverless, monitoreo, seguridad, escalabilidad, alta disponibilidad y comunicación con los sistemas bancarios existentes.

Prompt inicial

PROMPT INICIAL

Actúa como arquitecto de soluciones Cloud. Diseña una arquitectura para una aplicación de banca móvil utilizando una estrategia de nube híbrida.

La solución deberá incluir aplicación móvil, API Gateway, servicios backend, autenticación, bases de datos, almacenamiento, funciones serverless/FaaS, monitoreo y mecanismos de seguridad.

Identifica qué componentes deberían permanecer on-premises y cuáles deberían ejecutarse en la nube, justificando cada decisión.

Propón una arquitectura escalable, tolerante a fallos y altamente disponible.

Genera un diagrama de arquitectura y desarrolla un prototipo básico del backend. Explica cada componente y las decisiones arquitectónicas realizadas.

05

Proceso de Prompt Engineering

PROMPT 1

Seguridad

Prompt

Analiza la arquitectura propuesta desde el punto de vista de ciberseguridad para una institución financiera. Identifica vulnerabilidades y agrega mecanismos de protección de APIs, autenticación, cifrado, protección de credenciales, redes privadas y detección de amenazas.

Resultado

Se incorporaron AWS WAF, Amazon Cognito, AWS KMS, AWS Secrets Manager, IAM con principio de mínimo privilegio, Security Groups, subredes privadas, AWS CloudTrail y Amazon GuardDuty.

PROMPT 2

Alta disponibilidad

Prompt

Revisa la arquitectura e identifica todos los posibles puntos únicos de falla. Modifica la solución para que pueda continuar funcionando ante la caída de un servidor, zona de disponibilidad o conexión de red.

Resultado

Se incorporaron múltiples Availability Zones, backend distribuido, Aurora Multi-AZ, conexiones redundantes, Auto Scaling y servicios administrados.

PROMPT 3

Escalabilidad

Prompt

Optimiza la arquitectura para soportar desde algunos cientos hasta cientos de miles de usuarios simultáneos sin tener que aumentar manualmente la infraestructura.

Resultado

Se incorporaron Amazon API Gateway, AWS Lambda, Auto Scaling, Amazon CloudFront, Amazon S3 y Amazon ElastiCache cuando sea necesario.

PROMPT 4

Observabilidad

Prompt

Incorpora una estrategia completa de observabilidad. Necesito conocer errores, latencia, comportamiento de APIs, eventos de seguridad y disponibilidad de los componentes.

Resultado

Se incorporaron Amazon CloudWatch, AWS CloudTrail, logs, métricas, alarmas, trazabilidad de APIs y alertas de seguridad.

PROMPT 5

Recuperación ante desastres

Prompt

Diseña una estrategia de recuperación ante desastres para esta aplicación bancaria. Explica cómo proteger bases de datos, archivos y servicios en caso de una falla grave de infraestructura.

Resultado

Se agregaron backups automáticos, replicación de datos, versionamiento de objetos, copias de seguridad cifradas, recuperación de bases de datos, Infrastructure as Code y una estrategia de recuperación en una región secundaria.

PROMPT 6

Costos

Prompt

Analiza la arquitectura desde el punto de vista de costos. Reduce recursos innecesarios sin comprometer seguridad, disponibilidad ni rendimiento.

Resultado

Se priorizaron servicios administrados y serverless para evitar mantener infraestructura activa cuando no sea necesaria.

AWS Lambda se utiliza principalmente para procesos que se ejecutan bajo demanda.

PROMPT 7

Código

Prompt

Revisa el backend generado. Identifica problemas de seguridad, validación de datos, manejo de excepciones y exposición de información sensible. Modifica el código para que sea un prototipo más adecuado para una aplicación financiera.

Resultado

Se incorporaron validaciones, respuestas HTTP apropiadas, manejo de errores, separación de responsabilidades, gestión correcta de secretos y validación antes de operaciones sensibles.

Ejemplo del flujo de una operación

  1. El usuario abre la aplicación.
  2. El usuario inicia sesión.
  3. Amazon Cognito verifica su identidad.
  4. La aplicación envía una solicitud HTTPS.
  5. AWS WAF inspecciona el tráfico.
  6. Amazon API Gateway recibe la solicitud.
  7. El backend verifica autorización.
  8. La solicitud llega de forma segura a la infraestructura on-premises.
  9. Core Banking consulta el saldo.
  10. El backend recibe la información.
  11. API Gateway devuelve la respuesta.
  12. La aplicación muestra el saldo.

La aplicación móvil nunca se conecta directamente al Core Banking.

Prototipo Backend — Python + Flask

backend/app.pyVer archivo Python →
from flask import Flask, jsonify, request

app = Flask(__name__)

usuarios = {
    "1001": {
        "nombre": "Juan",
        "saldo": 15250.75
    }
}


@app.route("/health", methods=["GET"])
def health():
    return jsonify({
        "status": "ok",
        "service": "mobile-banking-api"
    }), 200


@app.route("/saldo/<usuario_id>", methods=["GET"])
def consultar_saldo(usuario_id):

    usuario = usuarios.get(usuario_id)

    if usuario is None:
        return jsonify({
            "error": "Usuario no encontrado"
        }), 404

    return jsonify({
        "usuario": usuario_id,
        "nombre": usuario["nombre"],
        "saldo": usuario["saldo"]
    }), 200


@app.route("/transferencia", methods=["POST"])
def transferencia():

    datos = request.get_json()

    if not datos:
        return jsonify({
            "error": "Solicitud inválida"
        }), 400

    origen = datos.get("origen")
    destino = datos.get("destino")
    monto = datos.get("monto")

    if not origen or not destino or monto is None:
        return jsonify({
            "error": "Faltan datos requeridos"
        }), 400

    try:
        monto = float(monto)
    except (ValueError, TypeError):
        return jsonify({
            "error": "Monto inválido"
        }), 400

    if monto <= 0:
        return jsonify({
            "error": "El monto debe ser mayor a cero"
        }), 400

    return jsonify({
        "mensaje": "Transferencia recibida para procesamiento",
        "origen": origen,
        "destino": destino,
        "monto": monto
    }), 202


if __name__ == "__main__":
    app.run(debug=True)

Explicación del código

El prototipo contiene tres endpoints principales.

GET /health

Permite verificar que el servicio se encuentre funcionando correctamente.

GET /saldo/<usuario_id>

Simula la consulta del saldo de un cliente.

POST /transferencia

Recibe una solicitud de transferencia y valida los datos necesarios antes de aceptar la operación.

En un ambiente real, el diccionario de usuarios utilizado en este prototipo sería sustituido por servicios internos y bases de datos autorizadas.

De igual manera, Flask no se ejecutaría utilizando debug=True en un ambiente de producción.

Reflexión individual

Aprendiendo sobre el uso de IA para diseñar una arquitectura Cloud

Cuando hablamos de Inteligencia Artificial en la actualidad, muchas veces podemos llegar a pensar que simplemente basta con escribir un prompt, esperar unos cuantos segundos y aceptar la respuesta que nos da la herramienta. Sin embargo, mediante esta actividad pude darme cuenta de que cuando hablamos de algo tan importante como la arquitectura de una aplicación bancaria, las cosas no son tan sencillas. La IA puede ser una herramienta bastante útil para ayudarnos a generar ideas y detectar cosas que probablemente no habíamos considerado, pero al final nosotros como ingenieros seguimos teniendo la responsabilidad de analizar si realmente lo que propone tiene sentido.

Prompt Engineering y cómo fue cambiando la solución

Al generar la primera arquitectura, la IA propuso una solución bastante sencilla que incluía la aplicación móvil, un API Gateway, servicios backend, una base de datos y comunicación con los sistemas internos del banco. A simple vista podía parecer suficiente, pero al comenzar a realizar prompts más específicos me fui dando cuenta de que todavía faltaban muchas cosas.

Por ejemplo, cuando le pedí que analizara la arquitectura desde el punto de vista de seguridad comenzaron a aparecer elementos como AWS WAF, Amazon Cognito, KMS, Secrets Manager y sistemas de monitoreo. Después, al preguntarle acerca de disponibilidad y puntos únicos de falla, la solución cambió nuevamente para considerar redundancia, múltiples zonas de disponibilidad y mecanismos de recuperación ante desastres.

Esto me ayudó a entender que entre más específica sea nuestra pregunta, más útil puede ser la respuesta de la IA. Es parecido a cuando le preguntas a alguien “¿mi computadora está bien?” y probablemente solo te diga que sí, pero si preguntas específicamente “¿mi computadora puede correr cierto videojuego con estas características?”, entonces la respuesta puede ser mucho más precisa.

¿La primera arquitectura realmente era adecuada?

En mi opinión, no completamente. La primera arquitectura servía como una base para comenzar, pero tenía varias omisiones importantes. Uno de los problemas principales era que no profundizaba lo suficiente en temas de seguridad, algo que resulta especialmente grave si estamos hablando de una institución financiera.

Imaginemos que una aplicación bancaria estuviera construida únicamente pensando en que los usuarios pudieran consultar su saldo y realizar transferencias, pero nadie hubiera pensado en qué ocurre si alguien intenta realizar miles de solicitudes maliciosas al sistema o consigue acceder a alguna contraseña almacenada incorrectamente. Aunque técnicamente la aplicación podría “funcionar”, claramente no podríamos considerarla una buena arquitectura.

Seguridad y errores encontrados

Uno de los aprendizajes que considero más importantes fue darme cuenta de que la seguridad no debe agregarse hasta el final, sino que debe formar parte de la arquitectura desde el principio.

Durante las diferentes iteraciones se detectaron problemas como falta de protección de las APIs, ausencia de un sistema de autenticación suficientemente definido, falta de mecanismos de auditoría y poca claridad sobre la conexión entre AWS y los sistemas que permanecerían dentro del banco.

Es así que la arquitectura terminó incluyendo herramientas como Amazon Cognito para autenticación, AWS WAF para proteger las APIs, CloudTrail para registrar acciones realizadas dentro de AWS y Secrets Manager para evitar guardar contraseñas directamente dentro del código.

¿Comprendo realmente el código generado?

En cuanto al código, considero que es muy importante no cometer el error de pensar que porque un código generado por IA funciona significa automáticamente que está listo para utilizarse en producción.

El prototipo realizado permite consultar información y recibir solicitudes de transferencia, pero todavía existen muchas cosas que tendrían que agregarse en un sistema bancario real, como autenticación, autorización, conexión con una base de datos segura, prevención de transferencias duplicadas, auditoría y controles antifraude.

Por ejemplo, sería parecido a realizar una página sencilla para una tienda donde puedes agregar productos al carrito. Puede funcionar perfectamente como demostración, pero eso no significa que ya estés listo para almacenar tarjetas de crédito de miles de clientes.

Validación y papel del ingeniero

Otro punto importante fue aprender que no debemos aceptar automáticamente las recomendaciones de la IA. Para validar la arquitectura fue necesario revisar para qué servía cada servicio y preguntarnos si realmente tenía sentido agregarlo.

Aquí es donde considero que entra uno de los papeles más importantes de un Ingeniero en Tecnologías Computacionales. Debemos contar con conocimientos de programación, redes, bases de datos, arquitectura y seguridad para ser capaces de identificar cuándo una propuesta es correcta y cuándo únicamente parece convincente.

La IA puede ayudarnos a generar código inicial, recomendar servicios, encontrar posibles errores e incluso ayudarnos a documentar una solución, pero decisiones importantes relacionadas con seguridad, información financiera, riesgos y puesta en producción deberían mantenerse bajo responsabilidad humana.

Conclusiones

Mediante esta actividad aprendí que utilizar Inteligencia Artificial no significa simplemente aceptar la primera respuesta que obtenemos. El Prompt Engineering puede ayudar bastante a mejorar una solución si sabemos realizar preguntas más específicas y analizar cada respuesta que recibimos.

También comprendí que una arquitectura Cloud no se trata solamente de conectar diferentes servicios, sino de considerar factores como seguridad, disponibilidad, escalabilidad, monitoreo y recuperación ante fallos.

Finalmente, considero que la IA puede convertirse en una herramienta bastante poderosa para nosotros como futuros ingenieros, pero únicamente cuando contamos con los conocimientos necesarios para revisar lo que genera. Una persona sin bases sólidas podría obtener una arquitectura que visualmente parece completa y aun así no detectar errores importantes.

Por lo que puedo decir que el verdadero valor de la IA no está en reemplazar al ingeniero, sino en permitirnos trabajar de una manera más rápida y explorar diferentes soluciones, mientras nosotros seguimos siendo responsables de comprender, revisar, probar, validar, corregir y justificar las decisiones que finalmente se utilicen.

17

Conclusiones de la actividad

La actividad permitió observar cómo una arquitectura generada inicialmente con ayuda de Inteligencia Artificial puede evolucionar considerablemente mediante Prompt Engineering. Las diferentes iteraciones permitieron detectar problemas de seguridad, disponibilidad, escalabilidad, monitoreo y recuperación ante desastres.

La versión final no solamente conecta servicios Cloud, sino que busca justificar el papel de cada componente y separar adecuadamente la infraestructura Cloud de los sistemas bancarios que permanecen on-premises.

El principal aprendizaje fue comprender que la IA puede ayudar a diseñar y analizar soluciones, pero la responsabilidad de revisar, validar y justificar las decisiones continúa siendo del ingeniero.

Doy mi palabra que he realizado esta actividad con integridad académica.
